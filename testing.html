Set up your project

Use Python 3.10 or later and a Moss staging project with inference access and a funded balance. Extract the zip, open a terminal in the kit folder and run the following commands. The activation command shown is for macOS or Linux.

python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export MOSS_PROJECT_ID="your_test_project_id"
export MOSS_PROJECT_KEY="your_test_project_key"

Check your first stream

python inference.py --plain --output first-stream.json

This sends one billable request to moss/fastlane-1. You can run it as soon as your project is funded and authorized. To try another enabled model, pass its ID with --model.

Pass when the model returns Ready and the stream reaches response.completed. The report records the model, time to the first text delta and total latency. Use multiple representative prompts before setting a latency budget. The overview’s sub-200 ms figure applies to supported fast-lane workloads.

Create a test index when you need grounding

python seed.py

Pass when the script prints Ready and index.json identifies the newly built index. The project keeps this index for later comparisons. The fixture contains six fictional documents and four labeled retrieval questions. If a seed fails after submission, check the index name in the manifest and review its build in the portal before creating another.

Check a grounded answer and an abstention

python inference.py --output answers-baseline.json

By default, the script sends two streamed requests to moss/fastlane-1 with the fixture index named and the reply cache disabled. It times the first nonempty text delta and completion from the start of the request. This measures client-observed inference latency. Provider caches and host state are outside the harness’s control.

Pass when the pickup answer contains LANTERN-42, the unsupported delivery-fee question yields Unknown, and both streams reach response.completed. Review the saved output text with your own cases. A matching phrase alone is a narrow smoke check for this fixture.

Measure cold and warm retrieval in your worker

This benchmark applies to applications using the retrieval SDK inside their own process. Hosted grounding searches the index on the Moss side of the inference request.

python evaluate.py --environment staging-worker-a --output baseline.json

Run on the class of worker you intend to deploy. This command runs serially. Each of three trials creates two fresh Python processes. Both use the same query settings and the same index. The report includes every raw timing in milliseconds and the expected document’s worst observed rank for each case.

MeasurementTiming boundary
Empty-cache index loadTime inside load_index in a new process with an empty index cache. The operating system and embedding model may already be warm.
Cached restartA second process uses the index cache populated by the first. The SDK can still check the cloud for changes. Review SDK or network logs to verify artifact reuse.
First queryThe first local query after each load, timed separately. Add the paired load and first-query samples if you need time through the first result.
Warm queryAfter priming all four cases, time five rounds per process against the loaded index. Default total is 120 warm samples. Report median and nearest-rank p95.

Pass when every case returns its labeled ID in the first two results on every attempt. Check load and warm timings against budgets for your hardware. A nonzero exit on a missed document leaves a report with the returned IDs.

For your own corpus, update the documents and expected IDs in fixture.json before seeding a new test index in a fresh kit folder. Set --alpha, --top-k, --trials and --rounds to match your test plan. Keep these settings fixed for a release comparison.

Time a query inside your worker

Use this Python snippet inside an async worker after creating its MossClient and selecting the index for the current room. Run the load once, then record each query’s duration on the turn where it runs.

from time import perf_counter
from moss import QueryOptions

await client.load_index(index_name, cache_path=cache_directory)
start = perf_counter()
hits = await client.query(index_name, user_text, QueryOptions(top_k=2, alpha=0.8))
query_ms = (perf_counter() - start) * 1000
print(query_ms, [doc.id for doc in hits.docs])

Compare an SDK release

Repeat the first-stream check with the candidate SDK using a new output filename. If your application uses retrieval, compare the same index and labeled cases as well.

Keep the old environment and its passing baseline. In a second environment, install the candidate SDK and compatible core, reuse the same folder and index, and run the commands below. Use a fresh output path for each run.

python evaluate.py --environment staging-worker-a --output candidate.json
python compare.py baseline.json candidate.json --max-slowdown-pct 20
python inference.py --output answers-candidate.json

The 20% margin is an example. Choose a tolerance from repeat runs on your own workers. You can also set --warm-p95-budget-ms to your application’s absolute budget. The comparison covers all five reported load, first-query and warm-p95 metrics. Compare both answer reports and review timing with enough samples for your workload.

Pass when every required case still passes and the selected timing budgets hold. The comparator returns 0 on pass, 1 on regression and 2 on an invalid or incomparable report. A baseline with missed cases cannot qualify a release. Check raw samples when a short run breaches a threshold.

Verify a voice call in your framework

ScenarioPass condition
First call after a restartThe correct room’s index is ready before lookup. Trace the time from the end of the user’s speech to the first audible agent response and compare with the voice budget.
Known policy and follow-upThe caller hears the fixture fact once, and the follow-up uses the intended context. The trace shows a single intended retrieval path for the turn.
Interruption and restartInterrupt the answer mid-sentence. Old speech stops, the next turn uses current context, and a delayed or failed lookup follows your configured fallback.
Two simultaneous roomsUse distinct test facts in each room. Each speaks only its own fact, stays within the latency budget and releases room-specific resources when the call ends.

The Python timing harness measures serial retrieval. Record framework, plug-in and worker versions alongside a real call trace and test production concurrency separately.

Resolve a failed run

  • If authentication fails, check that the project ID and key are from the same staging project and inference is enabled. Check Billing for exhausted credits.
  • For a retrieval miss, inspect miss_ids in the trial report and check the index, query text, expected ID, top K and alpha. Repeat with one change at a time.
  • For slow restarts, check the mounted cache path, its contents, the index revision and cloud availability. Measure multiple restarts before setting a threshold.
  • If a stream fails or ends early, inspect the case’s error type and terminal event. Test rollback or fallback in your application before increasing traffic.
